## 1. 我的总体目标

我希望代码系统不仅“当前能跑”，还要让我在几个月后重新打开时，能够快速知道：

- 从哪里进入。
- 当前运行的是哪个任务和批次。
- 每张表是什么用途。
- 每张表一行代表什么。
- 数据来自哪里、写到哪里。
- 哪些是本次工作，哪些是历史事实。
- 哪些结果已经执行并验证，哪些还只是计划。
- 同一任务重跑是否安全。

用户看到的操作入口应尽量少；内部可以有多个逻辑分支，但必须由代码自动路由，并最终汇合到统一的工作台或事实表。

## 2. 核心逻辑偏好

### 2.1 一个入口，多个内部逻辑，一个统一结果

当一个业务任务存在多个处理逻辑时：

1. 用户只从一个入口提交任务。
2. 代码根据明确字段自动判断应进入哪个逻辑。
3. 各逻辑完成补充和计算后，汇总到同一个 Work/Plan 表。
4. 用户在统一工作台完成人工确认。

不要要求用户分别进入多个文件，手工判断该跑哪套 notebook。

### 2.2 代码步骤不能成为业务依赖

下游任务不应依赖“Cell 6”“Step 2”之类的实现细节。

业务动作应使用稳定名称，例如：

- CREATE_BATCH
- BUILD_REFERENCE
- BUILD_DECISION_WORK
- CONFIRM_PLAN
- EXPAND_TO_SKU
- APPLY
- VERIFY
- WRITE_HISTORY
- REVIEW

即使以后内部代码从两步改成五步，下游关系也不应改变。

### 2.3 本次、当前和历史必须明确分开

- 本次任务必须通过显式 `change_id` / `run_id` / `request_id` 确定。
- 不要用“今天”“当前表里留下的内容”“最新一条记录”代替正式批次。
- Work 表可以刷新或覆盖。
- Fact/Log 表保存历史事实，不应因刷新工作台而丢失。
- Current Snapshot 是当前状态，不代表历史事件。
- Report 是展示结果，不应反向成为业务事实源。

### 2.4 计划、执行和验证是不同状态

需要清楚区分：

- 准备调整。
- 已确认计划。
- 已生成写入指令。
- 已尝试写入。
- Shopify/外部系统返回成功。
- 已重新读取并验证。
- 已进入正式历史。

不能因为生成了 Edit/Plan 就直接视为已经完成业务动作。

### 2.5 历史事实优先以已验证结果为准

最终“已完成”历史应在 Verify 之后形成。

- 验证成功：记录为 VERIFIED / 已完成。
- 执行失败：保留失败尝试和原因。
- 部分成功：记录 PARTIAL，不得把整批视为完全成功。
- 分析层默认只读取达到所需状态的事实记录。

### 2.6 一张表只承担一种主要职责

避免一张表同时承担：历史事实、当前快照、人工输入、下一轮计划和展示报表。

如果确实需要给用户一个综合页面，应使用 View/Work 表汇总多个来源，而不是把人工字段直接塞进 Fact 表。

## 3. 表类型与命名语义

优先使用以下前缀，并保持语义一致：

### `Control__`

任务、批次、Controller 和运行开关。一行通常代表一个 batch/request/run。

### `Input__`

用户或外部系统提交的原始任务范围。只表达“要处理什么”，不承担复杂计算。

### `Ref__`

稳定参考数据、映射、规则或外部快照。必须说明来源、刷新时间和唯一键。

### `Cfg__`

业务规则、阈值、账户、路由、字段映射和运行配置。

### `Dim__`

去重后的业务维度。一行一个稳定实体，例如一个 SKU、Variant Base、Product 或 Category。

### `Work__`

本次任务的人工工作区，可以刷新。必须使用稳定主键保留人工字段。

### `Plan__`

已确认但尚未完成外部写入的执行计划。

### `Fact__`

可被分析和追溯的历史事实。禁止加入空白分隔行和纯展示格式。

### `Out__` / `Check__`

本次运行输出或核对结果。若需要历史，应再写入对应 Fact。

### `Report__`

给人阅读的格式化报表，可以包含货币符号、百分比、说明行和空白分隔行，但不得作为原始事实源。

### `QA__`

数据质量问题、冲突、缺失、回退和异常样例。

### `Runlog__`

任务运行记录和最终摘要。

不要用 `Fact` 命名仍需人工填写、会随刷新改变或包含展示行的表。

## 4. 数据建模偏好

### 4.1 先定义 Grain，再写代码

创建或修改任何表之前，先写清楚：

- 一行代表什么。
- 主键是什么。
- 是否允许重复。
- 如果重复，采用什么规则。
- 是覆盖、追加还是 upsert。

示例：

- 一行一个 Variant Base：主键 `Variant Base`。
- 一行一个批次中的 Variant Base：主键 `change_id + Variant Base`。
- 一行一个批次中的 SKU：主键 `change_id + SKU`。
- 一行一个月度 SKU：主键 `Month + SKU`。

### 4.2 默认幂等

同一批次重跑不应生成重复事实或重复外部写入。

- Work/Snapshot：同名清空重写或按主键 upsert。
- Fact：按业务唯一键 upsert，或使用不可重复的事件键。
- Apply：必须防止同一计划被无意重复执行。
- Append 前必须检查目标唯一键是否已经存在。

### 4.3 明确去重规则

不要简单 `drop_duplicates(keep="first")` 而不解释。

需要说明：

- 为什么重复。
- 哪些字段用于判断冲突。
- 采用最新、最早、最高优先级、最高完整度还是人工确认。
- 冲突是否进入 QA。

### 4.4 人工字段必须可安全保留

工作台重建时，人工填写字段必须通过稳定组合键回填，不能依赖行号。

推荐：

- 先读取旧 Work 表人工字段。
- 使用稳定业务键建立 lookup。
- 重建自动字段。
- 合并人工字段。
- 对无法回填或一对多冲突写入 QA。

### 4.5 原始数值与展示格式分离

Fact 中保存纯数值和标准日期：

- 金额保存数值，不保存 `$1,234` 字符串。
- 比率保存 `0.18`，Report 再显示为 `18%`。
- 日期使用统一标准格式。
- 不在 Fact 中插入说明行、环比展示行或空白行。

## 5. Controller 与 Colab 偏好

### 5.1 Cell 1 集中配置

所有日常需要调整的内容集中在 Cell 1：

- SITE_CODE
- JOB_NAME
- NOTEBOOK_VERSION
- RUN_STAGE / RUN_MODE
- TARGET_CHANGE_ID / TARGET_REQUEST_ID
- 日期范围
- DRY_RUN
- CONFIRMED
- 写入开关
- 刷新 Ref 开关
- 阈值、倍数、分页大小
- Sheet label / URL

其他 Cell 不应要求用户修改常量。

### 5.2 禁止交互式弹窗和阻塞输入

- 不使用 `input()`。
- 不使用需要点击授权的临时认证流程。
- 使用 Colab Secrets、Service Account 和稳定 Token。
- Preview/Apply 通过 `DRY_RUN`、`CONFIRMED` 或明确 `RUN_STAGE` 控制。

### 5.3 主文件固定，版本备份明确

- 主 Colab 使用固定 URL 和稳定文件名。
- 日常更新直接更新主文件。
- 每次重要修改前创建版本备份。
- 备份命名：`主文件名__vYYYY.MM.DD.NN.ipynb`。
- notebook 顶部必须保留版本号与修改记录。
- 不创建 `final_v2_v3_latest_final` 一类无法判断顺序的文件。

### 5.4 Notebook 尽量薄

复杂项目优先采用：

1. Config / Controller
2. Load module
3. Run

业务逻辑拆成可测试函数或模块。Notebook 负责选择任务、展示预览和输出摘要。

如果暂时不能模块化，修改时应提供完整可替换 Cell，不要只给零散代码片段让用户手工拼接。

### 5.5 一个主入口，后台多个任务

用户可以只维护一个主 Controller notebook，通过 `RUN_STAGE` 选择业务阶段；后台可调用不同函数模块。

不要为了内部实现方便，让用户记住许多入口 URL 和执行顺序。

## 6. Google Sheets 与文件路由偏好

### 6.1 使用统一路由表

- 通过稳定 `sheet label` 找 URL。
- 全系统只保留一套权威路由，不应同时依赖多个 Console Core。
- 代码不得通过模糊标题猜目标文件。
- 运行摘要应打印最终解析到的工作簿和 Tab。

### 6.2 不随意新建 Tab

- 默认使用既定 Tab。
- 输出表存在时同名覆盖、清空重写或按主键 upsert。
- 只有明确设计新增表时才创建 Tab。
- 旧表需要归档时使用明确时间版本名，不要悄悄改名。

### 6.3 写入前检查表头和容量

- 先读取准确表头。
- 校验必填字段。
- 写入前扩容，避免 Range exceeds grid limits。
- 大表分块写入并处理 429/限流。
- 写完打印实际 range、行数、列数和批次数。

### 6.4 三层表头适合人工工作台

人工 Work 表可以使用：

1. 中文业务字段名
2. 稳定英文 field key
3. 字段说明/公式口径

代码读取稳定 field key；用户主要查看中文字段名和说明。

## 7. 日志、QA 与运行摘要

### 7.1 每次运行必须可追踪

至少打印：

- site_code
- job_name
- notebook/module version
- run_id
- run_stage / run_mode
- target batch/request id
- dry_run / confirmed
- source files/tabs
- target files/tabs

### 7.2 最终摘要必须量化

至少包含：

- rows_loaded
- rows_pending
- rows_recognized
- rows_planned
- rows_written
- rows_skipped
- warning_count
- failure_count
- duplicate_count
- missing_key_count
- output tab/file list
- status

### 7.3 正常结果与错误日志分开

- 不需要为每一条成功记录写 Runlog。
- Runlog 主要记录阶段摘要、失败和重要警告。
- 相同错误应去重，保留计数和一个有代表性的样例。
- 详细数据问题写入 `QA__DataIssues`。

### 7.4 何时硬停止

以下情况默认应停止：

- 缺少主键。
- 缺少外部写入所需 ID。
- 目标价格为空或不可解析。
- 同一业务唯一键出现冲突值。
- 同一实体生成重复写入指令。
- 路由到错误文件或找不到明确目标。
- 计划范围与执行范围不一致且无法解释。

以下情况通常只警告，不阻断：

- 缺少非核心展示字段。
- 少量无法匹配的分析行。
- 可解释的历史重复且已有确定选择规则。
- Ref 间汇总存在小额可容忍差异。

任何 fallback 都必须打印并写入 QA，不能静默发生。

## 8. 外部写入与安全偏好

### 8.1 默认 Preview → Confirm → Apply → Verify

推荐顺序：

1. 加载和识别。
2. 生成计划。
3. Preview。
4. Confirm。
5. Apply。
6. 重新读取外部系统。
7. Verify。
8. 写入最终历史。

### 8.2 Apply 与 Verify 必须分离

- API 返回成功不等于业务最终正确。
- Apply 后必须重新读取目标系统。
- Verification 应比较计划值与实际值。
- 只有达到验证标准后才标记 VERIFIED。

### 8.3 执行计划必须可审阅

在写入 Shopify、Google Sheets 或其他系统前，必须可以看到：

- entity_type
- entity ID
- field_key
- current_value
- desired_value
- action
- warning
- source batch

## 9. 分析逻辑偏好

### 9.1 分析只能依赖业务事实，不依赖中间步骤

Review/Impact Analysis 不应读取某个 notebook 的 Step 2 临时产物。

分析层应读取：

- 已确认或已验证的 Fact。
- 标准 Dim。
- 标准日/月销售事实。
- 明确 Controller 时间范围。

### 9.2 状态口径必须统一

例如调价系统：

- 生成计划不等于已调价。
- Apply 成功但未验证时是待验证。
- VERIFIED 后才算已调价。
- 月度状态需要明确是“当月发生调价”还是“截至当月已经调价”。

### 9.3 静态字段不要跨月份重复累计

- Count 按唯一实体计数。
- Cost、Price、调前价、调后价等静态字段应一实体只计一次，除非分析明确要求月度快照。
- Net Sales、Units 等流量事实按 Controller 范围汇总。
- Eligible 指标必须说明覆盖范围和排除原因。

### 9.4 内部核对优先

聚合输出前后需要对账：

- 明细合计 vs 汇总合计。
- 月度合计 vs 完整范围合计。
- Ref A vs Ref B 的关键指标。
- 唯一实体数是否一致。

可解释差异打印 WARNING，不应无说明忽略。

## 10. 重构与迁移偏好

### 10.1 迁移业务逻辑，不复制旧架构

重构时应分别判断：

- 可复用的业务规则。
- 可复用的数据拉取函数。
- 可复用的清洗与校验。
- 需要淘汰的文件复制和隐式联动。
- 需要升级的数据模型。

### 10.2 先做 Data Contract

写代码前先建立：

- 旧表 → 新表映射。
- 旧字段 → 新字段映射。
- 每张表的 grain、key、来源和刷新方式。
- 任务依赖关系。
- Cutover 和回滚方案。

### 10.3 使用 Golden Test Batch

选取一小批代表性数据同时跑新旧系统，至少覆盖：

- 不同逻辑分支。
- 普通行和组合/倍数行。
- 缺字段和冲突数据。
- 需要 CLEAR/DELETE 的动作。
- 多次历史事件。
- 成功、失败、部分成功。

比较最终计划、写入指令和验证结果后再正式切换。

### 10.4 旧系统保留只读

- 新系统稳定前不删除旧文件。
- Cutover 后停止旧系统写入。
- 旧文件改为 Legacy/Archive，并保留查询能力。
- 新系统成为唯一写入源。

## 11. 明确不喜欢的实现方式

- 同一份 Fact/Log 在多个工作簿中复制。
- 用日期或当前行位置猜本次批次。
- 下游直接依赖 Cell 编号或 Step 编号。
- 同一批次重跑后重复 append。
- 空白状态被当作有效状态。
- Fact 混入人工输入、货币字符串、说明行和空白分隔行。
- 一张表既是输入、工作台、历史、分析结果又是下一轮计划。
- 为每个内部逻辑建立一个用户入口。
- 每次修改创建一个无法判断顺序的新主文件。
- 用零散代码片段要求用户手工拼接复杂逻辑。
- fallback、去重或缺失匹配静默发生。
- 代码运行成功但没有最终摘要和 QA。

## 12. Codex 交付代码时的默认要求

### 修改现有系统

1. 先读取现有文件、字段、运行日志和上下游关系。
2. 区分“现有实际实现”和“计划中的设计”。
3. 说明根因、影响范围和迁移方式。
4. 尽量保留正确的现有行为。
5. 不顺手改动无关模块。
6. 完成后执行与风险匹配的验证。

### 交付内容

- 明确修改了什么。
- 明确没有修改什么。
- 给出完整替换文件或完整替换 Cell。
- 给出 Controller 使用方法。
- 给出 Preview/Apply 方法。
- 给出预期运行摘要。
- 给出已知 warning 和下一步。

### 需要用户确认的情况

只有当选择会实质改变业务结果、数据口径或外部写入范围时才需要暂停询问。普通实现细节应依据本文档和项目 Data Contract 自主推进。

## 13. 项目专用补充模板

每个项目可以另外建立项目级 `AGENTS.md`，并引用本文档。项目级文件至少补充：

```text
Project Name:
Site Code:
Main Controller URL/File:
Router URL/File:
Source of Truth:
Primary Business Key:
Current Workflow Stages:
External Systems:
Secrets Names:
Allowed Write Targets:
Forbidden Write Targets:
Required QA Checks:
Cutover / Rollback Rules:
Project-Specific Business Rules:
```

本文档负责通用偏好；项目级 `AGENTS.md` 负责具体业务事实和当前系统结构。若两者冲突，以项目级明确业务要求和用户最新指令为准。

## 14. 使用方式

推荐以下任一方式：

1. 开始新项目时把本文档提供给 Codex。
2. 将本文档复制到项目文档目录，并在根目录 `AGENTS.md` 中引用。
3. 从本文档提取适用于当前项目的规则，形成精简版项目 `AGENTS.md`。
4. 随着新项目暴露新的稳定偏好，继续更新本文档版本，而不是在不同对话里重新描述。

这是一份长期协作契约，不是某个项目的一次性需求说明。
