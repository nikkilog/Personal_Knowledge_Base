## 1. 我的总体目标

我希望代码系统不仅“当前能跑”，还要让我在几个月后重新打开时，能够快速知道：

- 从哪里进入。
- 当前运行的是哪个任务和批次。
- 每张表是什么用途。
- 每张表一行代表什么。
- 数据来自哪里、写到哪里。
- 哪些是本次工作，哪些是历史事实。
- 哪些结果已经执行并验证，哪些还只是计划。
- 同一任务重跑是否安全。

同一业务任务的操作入口应清楚；内部可按规则自动路由。Notebook 的数量由实际业务任务与用户明确决定，已确认独立使用的入口保持独立，不为代码职责划分增加人工入口，也不强行合成巨型 Notebook。

## 2. 核心逻辑偏好

### 2.1 一个入口，多个内部逻辑，一个统一结果

当一个业务任务存在多个处理逻辑时：

1. 同一任务尽量从一个明确入口提交；不同且已确认独立使用的任务保留各自入口。
2. 代码根据明确字段自动判断应进入哪个逻辑。
3. 各逻辑完成补充和计算后，汇总到同一个 Work/Plan 表。
4. 用户在统一工作台完成人工确认。

不要要求用户分别进入多个文件，手工判断该跑哪套 notebook。

### 2.2 代码步骤不能成为业务依赖

下游任务不应依赖“Cell 6”“Step 2”之类的实现细节。

业务动作应使用稳定名称，例如：

- CREATE_BATCH
- BUILD_REFERENCE
- BUILD_DECISION_WORK
- CONFIRM_PLAN
- EXPAND_TO_SKU
- APPLY
- VERIFY
- WRITE_HISTORY
- REVIEW

即使以后内部代码从两步改成五步，下游关系也不应改变。

### 2.3 本次、当前和历史必须明确分开

- 本次任务必须通过显式 `change_id` / `run_id` / `request_id` 确定。
- 不要用“今天”“当前表里留下的内容”“最新一条记录”代替正式批次。
- Work 表可以刷新或覆盖。
- Fact/Log 表保存历史事实，不应因刷新工作台而丢失。
- Current Snapshot 是当前状态，不代表历史事件。
- Report 是展示结果，不应反向成为业务事实源。

### 2.4 计划、执行和验证是不同状态

需要清楚区分：

- 准备调整。
- 已确认计划。
- 已生成写入指令。
- 已尝试写入。
- Shopify/外部系统返回成功。
- 已重新读取并验证。
- 已进入正式历史。

不能因为生成了 Edit/Plan 就直接视为已经完成业务动作。

### 2.5 历史事实优先以已验证结果为准

最终“已完成”历史应在 Verify 之后形成。

- 验证成功：记录为 VERIFIED / 已完成。
- 执行失败：保留失败尝试和原因。
- 部分成功：记录 PARTIAL，不得把整批视为完全成功。
- 分析层默认只读取达到所需状态的事实记录。

### 2.6 一张表只承担一种主要职责

避免一张表同时承担：历史事实、当前快照、人工输入、下一轮计划和展示报表。

如果确实需要给用户一个综合页面，应使用 View/Work 表汇总多个来源，而不是把人工字段直接塞进 Fact 表。

## 3. 表类型与命名语义

优先使用以下前缀，并保持语义一致：

### `Control__`

任务、批次、Controller 和运行开关。一行通常代表一个 batch/request/run。

### `Input__`

用户或外部系统提交的原始任务范围。只表达“要处理什么”，不承担复杂计算。

### `Ref__`

稳定参考数据、映射、规则或外部快照。必须说明来源、刷新时间和唯一键。

### `Cfg__`

业务规则、阈值、账户、路由、字段映射和运行配置。

### `Dim__`

去重后的业务维度。一行一个稳定实体，例如一个 SKU、Variant Base、Product 或 Category。

### `Work__`

本次任务的人工工作区，可以刷新。必须使用稳定主键保留人工字段。

### `Plan__`

已确认但尚未完成外部写入的执行计划。

### `Fact__`

可被分析和追溯的历史事实。禁止加入空白分隔行和纯展示格式。

### `Out__` / `Check__`

本次运行输出或核对结果。若需要历史，应再写入对应 Fact。

### `Report__`

给人阅读的格式化报表，可以包含货币符号、百分比、说明行和空白分隔行，但不得作为原始事实源。

### `QA__`

数据质量问题、冲突、缺失、回退和异常样例。

### `Runlog__`

任务运行记录和最终摘要。

不要用 `Fact` 命名仍需人工填写、会随刷新改变或包含展示行的表。

## 4. 数据建模偏好

### 4.1 先定义 Grain，再写代码

创建或修改任何表之前，先写清楚：

- 一行代表什么。
- 主键是什么。
- 是否允许重复。
- 如果重复，采用什么规则。
- 是覆盖、追加还是 upsert。

示例：

- 一行一个 Variant Base：主键 `Variant Base`。
- 一行一个批次中的 Variant Base：主键 `change_id + Variant Base`。
- 一行一个批次中的 SKU：主键 `change_id + SKU`。
- 一行一个月度 SKU：主键 `Month + SKU`。

### 4.2 默认幂等

同一批次重跑不应生成重复事实或重复外部写入。

- Work/Snapshot：同名清空重写或按主键 upsert。
- Fact：按业务唯一键 upsert，或使用不可重复的事件键。
- Apply：必须防止同一计划被无意重复执行。
- Append 前必须检查目标唯一键是否已经存在。

### 4.3 明确去重规则

不要简单 `drop_duplicates(keep="first")` 而不解释。

需要说明：

- 为什么重复。
- 哪些字段用于判断冲突。
- 采用最新、最早、最高优先级、最高完整度还是人工确认。
- 冲突是否进入 QA。

### 4.4 人工字段必须可安全保留

工作台重建时，人工填写字段必须通过稳定组合键回填，不能依赖行号。

推荐：

- 先读取旧 Work 表人工字段。
- 使用稳定业务键建立 lookup。
- 重建自动字段。
- 合并人工字段。
- 对无法回填或一对多冲突写入 QA。

### 4.5 原始数值与展示格式分离

Fact 中保存纯数值和标准日期：

- 金额保存数值，不保存 `$1,234` 字符串。
- 比率保存 `0.18`，Report 再显示为 `18%`。
- 日期使用统一标准格式。
- 不在 Fact 中插入说明行、环比展示行或空白行。

## 5. Controller 与 Colab 偏好

### 5.1 Controller 集中配置

在开头的运营使用说明之后，进入 Controller 参数区。既有 Notebook 的 Cell 编号以项目 Current 为准，增加说明时不能让编号引用或运行顺序失效。将日常需要调整且适用的内容集中在 Controller：

- SITE_CODE
- JOB_NAME
- NOTEBOOK_VERSION
- RUN_STAGE / RUN_MODE
- TARGET_CHANGE_ID / TARGET_REQUEST_ID
- 日期范围
- DRY_RUN
- CONFIRMED
- 写入开关
- 刷新 Ref 开关
- 阈值、倍数、分页大小
- Sheet label / URL

其他 Cell 不应要求用户反复修改隐藏常量。

### 5.2 日常认证与运行接手

- 先查项目入口、运行说明、代码、配置和依赖；已有清楚记录直接沿用，不重复问用户“项目怎么跑”。项目资料缺失、冲突或确需改变时，只问具体缺口。
- 日常运行沿用现有认证配置，优先非交互执行；不得静默改成弹窗、手动登录、新身份或新认证路线。初次环境配置、授权维护与日常运行分开说明，不能把一次初始化步骤写成每次运行必做。
- 不在长任务中途才触发必要交互。现有配置确实无法完成认证时，指出实际缺口和依据；不得借用其他项目凭据、猜 Secret 来源或补造方案。需要重新授权时按项目真实合同和风险处理，不能把“用户点击 OAuth”写成用户偏好。
- 避免无必要的阻塞式 `input()`；适用时通过 `DRY_RUN`、`CONFIRMED` 或 `RUN_STAGE` 控制 Preview/Apply。认证机制、身份、scope 和 Secret 来源以项目 Current 为准，不把 Service Account、Colab Secrets 或某种 Token 当成所有项目的统一答案。

### 5.3 主文件与必要备份

- 主 Colab 使用固定 URL 和稳定文件名。
- 日常更新直接更新主文件。
- 覆盖正式数据、不可逆写入、缺少可靠恢复点或非 Git 资产发生重大修改时，先取得适用的备份或回滚点；已有充分版本历史、可逆且可重跑时不为形式重复制造副本。
- 确需单独保存 Notebook 备份时，可用可排序、能识别来源和时间的名称；普通编辑历史交给 Git。Notebook 内部保留适用的版本与变更说明。
- 不创建 `final_v2_v3_latest_final` 一类无法判断顺序的文件。

### 5.4 Notebook 结构按实现形态决定

Notebook 打开后的第一部分优先放简短的中文运营使用说明，再进入 Controller 参数区和执行代码。说明按实际需要交代用途、运行前要准备的资料或条件、需修改的参数与允许值（必要时给示例）、运行方法及写入/覆盖影响、结果位置与成功判断，以及出错、中断或重跑的处理。逐项内容必须与当前代码真实行为一致，不声称尚未实现的功能，也不为凑模板填写无用项目。技术架构、开发说明和版本历史放在后续位置或相关文档，不占据运营说明的开头。说明可用 Markdown Cell；它不决定 Notebook 的代码 Cell 数量或编号。

当 Notebook 是外部 Python 模块或本地包的薄入口时，可按可选 Registry（默认关闭）、集中配置的 Controller、认证/依赖/加载、执行/摘要组织功能。既有 4 Cell 代码入口及 `Cell 0`–`Cell 3` 的引用须按项目 Current 核对；说明放在最前面时，适用的编号、链接和运行指引要同步准确。功能分工不强制所有 Notebook 使用相同的物理 Cell 数量。共享 Python 没有某项目专用 Notebook 入口，不等于能力缺失。

业务逻辑保存在独立 `.ipynb` 时，按 Controller、Runtime/依赖、认证、核心处理、读取、写入、执行与摘要等真实功能自然拆分。每个 Cell 职责清楚、长度适中、可顺序运行；可测试的业务逻辑适合抽成函数或模块，但不为此额外制造人工入口。主流程不依赖中途手工改隐藏变量。

如果暂时不能模块化，修改时应提供完整可替换 Cell，不要只给零散代码片段让用户手工拼接。

### 5.5 入口数量由业务任务决定

一个业务任务有多个内部阶段时，可由一个 Controller 通过 `RUN_STAGE` 路由；已经确认需要独立启动、验收或重跑的任务保留独立入口。不要让用户为内部函数拆分记住额外 URL 和执行顺序，也不要因“文件少”牺牲真实职责边界。见 P021、P078。

### 5.6 Colab 与本地运行

- 用户需要同一本 Notebook 在所要求的线上、线下环境运行；主要环境包括 Google Colab 和本机 VS Code/Jupyter 及已有 Python 环境。保持一份业务逻辑，按环境处理依赖、路径、模块加载和 Secret 来源。文档应分别说明支持目标、配置前提和两端实际验收状态；需要支持不等于已经两端运行通过，也不承诺未配置环境自然兼容。见 P034、P035。
- 优先沿用项目现有环境、代码、认证与依赖，不擅自要求新建环境、申请权限或再配置一套 Secret。解释器路径、环境名、运行入口、模块加载和验收记录由项目 Current 持有，不在 PKB 补造。
- Notebook Registry 若存在，是默认关闭且不阻断主任务的辅助能力。启用时按项目定义的逻辑唯一键精确定位；已有 `job_name + sheet_label + Tab name` 合同的项目沿用该键。零条或多条匹配只告警，不任意追加或修改；唯一匹配才更新。只有操作者显式启用 strict 才可让登记异常中止主任务。URL 和名称等易变字段可同步；用途、排序、说明、审核状态、逻辑键和会改变 Job 行为的主要操作字段由人工维护，不罗列普通输入列。
- 跨项目共用能力应通过明确的共享组件、配置和身份边界接入；历史特例不反向定义通用框架。Secret 名称适配放在统一 Loader 或认证边界，不散落于各 API 调用点；只解析当前项目明确允许的来源，不扫描或混用其他项目配置。
- 曾明确约定的 Google OAuth 配置键为 `CAH_DRIVE_CLIENT_ID`、`CAH_DRIVE_CLIENT_SECRET`、`CAH_DRIVE_REFRESH_TOKEN`，`CAH` 不随目标项目名自动替换。接入时仍以项目 Current 核对正式来源、授权身份、scope 与目标资源；此约定不证明凭据可用，也不授权迁移或改写配置。需新建或维护本地 Secret 时，避免值进入聊天、命令历史和日志；经授权选用非回显输入、受控位置及最小权限，只报告不含值的检查结果。

### 5.7 表格公式

同类公式优先在首个适用单元格写入模板或入口公式，再用表格自身的向下填充、批量填充或扩展机制覆盖目标范围；Notebook 不逐行拼接并逐行写入同类公式。能由一个公式覆盖整列时用适用的整列扩展方式；需要相对引用时用模板与批量填充，不强制使用 `ARRAYFORMULA`。按项目实际表格核对相对/绝对引用、数据起始行、空行、范围边界和人工内容保护。本条是建设偏好，不代表既有 Notebook 已按此实现。

## 6. Google Sheets 与文件路由偏好

### 6.1 使用统一路由表

- 通过稳定 `sheet label` 找 URL。
- 同一工作流只保留一套权威路由，不并行维护互相冲突的路由来源。
- 代码不得通过模糊标题猜目标文件。
- 运行摘要应打印最终解析到的工作簿和 Tab。

### 6.2 不随意新建 Tab

- 默认使用既定 Tab。
- 输出表存在时保持正式 Tab 身份；全量覆盖、追加或按主键 upsert 由业务合同、幂等键、历史保留要求和人工字段保护决定。全量替换才按确认的范围清空/覆盖；不能从“目标稳定”推导出所有表都应清空重写。
- 只有明确设计新增表时才创建 Tab。
- 旧表是否需备份或归档由独立追溯与恢复价值决定；不得悄悄改名或默认生成历史副本。

### 6.3 写入前检查表头和容量

- 先读取准确表头。
- 校验必填字段。
- 写入前扩容，避免 Range exceeds grid limits。
- 大表分块写入并处理 429/限流。
- 写完打印实际 range、行数、列数和批次数。

### 6.4 三层表头适合人工工作台

人工 Work 表可以使用：

1. 中文业务字段名
2. 稳定英文 field key
3. 字段说明/公式口径

代码读取稳定 field key；用户主要查看中文字段名和说明。

## 7. 日志、QA 与运行摘要

### 7.1 每次运行必须可追踪

按任务适用范围记录可追溯的身份、阶段、来源和目标，例如：

- site_code
- job_name
- notebook/module version
- run_id
- run_stage / run_mode
- target batch/request id
- dry_run / confirmed
- source files/tabs
- target files/tabs

### 7.2 最终摘要必须量化

按任务实际阶段选择字段，而非把以下项目机械设为所有 Notebook 的必填模板：

- rows_loaded
- rows_pending
- rows_recognized（仅有独立“识别”阶段时）
- rows_planned
- rows_written
- rows_no_change（存在幂等无操作时）
- rows_skipped
- rows_failed
- warning_count
- failure_count
- duplicate_count
- missing_key_count
- output tab/file list
- status

运行环境、认证类型、是否使用交互、业务对象数、计划/成功/失败的 API 操作数和实际输出视图，应在相关任务中同时报告；适用字段包括 `runtime_mode`、`auth_type`、`interactive_auth_used`、`business_objects_planned`、`api_operations_planned`、`api_operations_succeeded`、`api_operations_failed`。这些不同于输入行数或写入行数。

输入行、通过校验的行、计划业务对象、计划 API 操作、成功/失败的 API 操作与实际写入行必须按真实语义区分；多个输入行可能合并为一个操作。`NO_CHANGE`、`ALREADY_CORRECT` 等原本已满足目标状态的幂等无操作记入 `rows_no_change`；`rows_skipped` 表示因范围、规则或门禁未进入计划/执行，`rows_failed` 表示处理失败。摘要应让操作者直接区分实际改变、无需改变、跳过和失败。

### 运行中进度与故障证据

较长运行通过阶段、批次或适度 heartbeat 持续反馈已完成/总量、当前对象、成功/失败/跳过、warning/error、重试、限流等待和 partial failure；有足够信息时给出 ETA。错误和重试及时提示，避免逐行刷屏。可安全隔离的对象错误在日志和对应输出行记录稳定错误码、对象、分组、字段、冲突/缺失值及具体原因；同一对象的多个问题应累计。Schema、来源契约、关键配置、全局唯一性或会污染整批结果的结构性错误整体 fail fast。无法安全隔离的财务结算或不可逆批量写入不套用继续处理规则。

### 7.3 正常结果与错误日志分开

- 不需要为每一条成功记录写 Runlog。
- Runlog 主要记录阶段摘要、失败和重要警告。
- 相同错误应去重，保留计数和一个有代表性的样例。
- 详细数据问题写入 `QA__DataIssues`。

### 7.4 何时硬停止

以下情况默认应停止：

- 缺少主键。
- 缺少外部写入所需 ID。
- 目标价格为空或不可解析。
- 同一业务唯一键出现冲突值。
- 同一实体生成重复写入指令。
- 路由到错误文件或找不到明确目标。
- 计划范围与执行范围不一致且无法解释。

以下情况通常只警告，不阻断：

- 缺少非核心展示字段。
- 少量无法匹配的分析行。
- 可解释的历史重复且已有确定选择规则。
- Ref 间汇总存在小额可容忍差异。

任何 fallback 都必须打印并写入 QA，不能静默发生。

## 8. 外部写入与安全偏好

### 8.1 风险相称的 Preview → Confirm → Apply → Verify

对具有真实外部副作用或业务成本的写入，推荐按需采用：

1. 加载和识别。
2. 生成计划。
3. Preview。
4. Confirm。
5. Apply。
6. 重新读取外部系统。
7. Verify。
8. 写入最终历史。

低风险、可逆且已有授权的操作不为流程形式重复增加确认或全链路回读；必要门禁以项目合同与真实风险决定。

### 8.2 Apply 与 Verify 必须分离

- API 返回成功不等于业务最终正确。
- 当业务状态需要独立验收时，Apply 后重新读取目标系统，并比较计划值与实际值；具体回读强度按风险决定。
- 只有达到验证标准后才标记 VERIFIED。

### 8.3 执行计划必须可审阅

在写入 Shopify、Google Sheets 或其他系统前，必须可以看到：

- entity_type
- entity ID
- field_key
- current_value
- desired_value
- action
- warning
- source batch

### 8.4 写入边界、恢复与验证

- 大规模操作先完整读取并预检输入、批量读取当前事实，生成可审阅计划和 Preview，再经明确写入门分批执行；避免边读边盲写。Prepare 是计划快照，Apply 前重读会影响真实写入的关键配置、目标状态与冲突条件。
- 能安全分开且错误写入有实际业务成本的发布或同步，可按 `本地/只读预检 → 真实连接与认证验证（不变更数据）→ 明确写入确认` 推进；覆盖、替换等更强副作用单独授权，不机械套到低风险动作。高风险写入可用 Dry Run、对象/批次上限和安全草稿状态；部分失败保留安全状态并报告。
- 已有资产先做定向修复；结构不可修复或用户明确授权才重建。关键输入缺失、空读取、字段不符、写入不全或回读不一致，应显式失败，不吞异常或用空结果冒充成功。写后按真实风险核对行数、字段、汇总或目标状态。
- Google 写入和其他外部写入的备份按覆盖风险、可逆性、已有版本历史及恢复成本决定。批量查重若已有可信快照，优先一次读取任务必要身份键后在内存比对，不逐对象远程查询或扩展无关校验。可安全并行的对象允许有限并发，但保留对象级结果、失败隔离、进度和运行上限。
- 大量独立对象具备处理条件时，获批范围内可由一次启动自动处理所选或全部对象，底层仍可逐对象调用 API；不要求操作者逐个人工运行。运行模式、失败隔离和继续处理条件见 §7。
- Schema 变更同步模板、常量、读取、默认值、校验、处理、输出和说明。稳定字段标识、类型、表达式、聚合及清除规则可由统一配置驱动，只更新明确受管字段；用途、顺序、审核状态、业务分类及说明等人工字段应保护。历史实现有差异时，先区分真实行为、声明行为、计划能力、局部验证和遗留，不因结构不齐便重构。
- 能由代码可靠维护的运行状态、镜像、目标创建和容量扩充由代码处理，解释性资产由人工维护。业务阈值与映射集中定义，不散落于多个 Cell。仍处于设计、试验或局部验证的模块只证明相应局部能力，不能直接视为正式标准。

## 9. 分析逻辑偏好

### 9.1 分析只能依赖业务事实，不依赖中间步骤

Review/Impact Analysis 不应读取某个 notebook 的 Step 2 临时产物。

分析层应读取：

- 已确认或已验证的 Fact。
- 标准 Dim。
- 标准日/月销售事实。
- 明确 Controller 时间范围。

### 9.2 状态口径必须统一

例如调价系统：

- 生成计划不等于已调价。
- Apply 成功但未验证时是待验证。
- VERIFIED 后才算已调价。
- 月度状态需要明确是“当月发生调价”还是“截至当月已经调价”。

### 9.3 静态字段不要跨月份重复累计

- Count 按唯一实体计数。
- Cost、Price、调前价、调后价等静态字段应一实体只计一次，除非分析明确要求月度快照。
- Net Sales、Units 等流量事实按 Controller 范围汇总。
- Eligible 指标必须说明覆盖范围和排除原因。

### 9.4 内部核对优先

聚合输出前后需要对账：

- 明细合计 vs 汇总合计。
- 月度合计 vs 完整范围合计。
- Ref A vs Ref B 的关键指标。
- 唯一实体数是否一致。

可解释差异打印 WARNING，不应无说明忽略。

## 10. 重构与迁移偏好

### 10.1 迁移业务逻辑，不复制旧架构

重构时应分别判断：

- 可复用的业务规则。
- 可复用的数据拉取函数。
- 可复用的清洗与校验。
- 需要淘汰的文件复制和隐式联动。
- 需要升级的数据模型。

### 10.2 先做 Data Contract

写代码前先建立：

- 旧表 → 新表映射。
- 旧字段 → 新字段映射。
- 每张表的 grain、key、来源和刷新方式。
- 任务依赖关系。
- Cutover 和回滚方案。

### 10.3 使用 Golden Test Batch

选取一小批代表性数据同时跑新旧系统，至少覆盖：

- 不同逻辑分支。
- 普通行和组合/倍数行。
- 缺字段和冲突数据。
- 需要 CLEAR/DELETE 的动作。
- 多次历史事件。
- 成功、失败、部分成功。

比较最终计划、写入指令和验证结果后再正式切换。

### 10.4 旧系统保留只读

- 新系统稳定前不删除旧文件。
- Cutover 后停止旧系统写入。
- 旧系统有独立运营、恢复或追溯价值时保留只读查询或明确的 Legacy/Archive 身份；普通编辑历史由 Git 保留，不因退出 Current 就自动生成 Archive 副本。处置前列出候选、用途、去向与待迁移知识，并按仓库规则取得必要授权。
- 新系统成为唯一写入源。

## 11. 明确不喜欢的实现方式

- 同一份 Fact/Log 在多个工作簿中复制。
- 用日期或当前行位置猜本次批次。
- 下游直接依赖 Cell 编号或 Step 编号。
- 同一批次重跑后重复 append。
- 空白状态被当作有效状态。
- Fact 混入人工输入、货币字符串、说明行和空白分隔行。
- 一张表既是输入、工作台、历史、分析结果又是下一轮计划。
- 仅因内部逻辑拆分而增加用户入口，或强行合并已确认独立使用的业务任务。
- 每次修改创建一个无法判断顺序的新主文件。
- 用零散代码片段要求用户手工拼接复杂逻辑。
- fallback、去重或缺失匹配静默发生。
- 代码运行成功但没有最终摘要和 QA。

## 12. Codex 交付代码时的默认要求

### 修改现有系统

1. 先读取现有文件、字段、运行日志和上下游关系。
2. 区分“现有实际实现”和“计划中的设计”。
3. 说明根因、影响范围和迁移方式。
4. 尽量保留正确的现有行为。
5. 不顺手改动无关模块。
6. 完成后执行与风险匹配的验证。

### 交付内容

- 明确修改了什么。
- 给出与请求相符的完整替换文件或完整替换 Cell；1–2 个 Cell 的局部修复可直接提供完整 Cell，范围较大且用户已提供 Notebook 时交付可从头运行的完整文件，不让用户拼补丁。
- 给出 Controller 使用方法。
- 给出 Preview/Apply 方法。
- 给出预期运行摘要。
- 给出已知 warning、实际验证、未验证项和下一步；代码注释、配置说明与报错解释优先用中文，API 字段等专名保留原文。

### 文件格式、身份与环境

- 普通数据、导入表和批量结果优先 UTF-8 CSV。需要公式、多工作表、数据验证或其他 Excel 功能时用 XLSX 并保留必要功能；只有展示目的、实际可读性问题或用户明确要求时才做相称的样式与渲染。减少外观处理不减少字段、公式、编码及结构的正确性检查，且服从本轮指定格式与项目必要功能。
- 仓库 Current 使用稳定路径和名称，原位更新；外部聊天交付使用能与旧附件区分的新名称，但不能改变仓库正式模块、import 或路径身份。缓存防护、远程下载保存名、Runtime copy 与真实仓库模块身份的边界见 P054、P060。源码是 Current，Runtime copy 是执行副本，刷新与验证按项目合同执行。
- 本地 Runtime 目录保持清楚层级，Notebook 内部版本可在元数据或代码中记录。项目已有 Python 环境和依赖清单时先复用，不为任务擅自新建环境；虚拟环境与 Secret 分开管理，绝不提交或分发环境或 Secret 值。具体解释器、安装、加载和验收记录只由项目 Current 持有。
- Operator 型工具是否以 Google Sheets 为工作界面，是否将本地 CSV/XLSX 设为可选快照，以及长任务是否以本地文件为 Source of Truth，均依业务合同与现有实现决定。只有项目明确采用本地权威时，才先安全落盘并把线上表作为受控镜像；默认只同步正式业务输出，日志、失败明细和诊断文件是否上云按项目要求和授权决定。广告等会重新归因的数据在校验时区分可解释变动与真实异常，保留适用的严格模式。颜色与格式用于实际防错与阅读，不为装饰反复渲染。
- 正式 Notebook 名称应说明用途，适用时可用 `Create_`、`Build_`、`Run_`；项目专用 Skill 和入口清楚表达项目与用途。Python 默认使用 snake_case 命名变量/函数/模块、UPPER_SNAKE_CASE 命名常量、PascalCase 命名类；布尔值可用 is_/has_/should_/enable_/allow_ 前缀。注释重点解释原因，复杂函数应有 docstring。长期方法文档保存跨项目判断，项目交接文档保存真实输入输出、配置、验证、限制和下一步。

### 需要用户确认的情况

普通实现细节依据本文和项目 Data Contract 自主推进。会实质改变业务结果、数据口径、外部写入范围，或触及仓库规则要求单独授权的删除、归档、提交、发布与同步时，先核对当前任务是否已经明确授权；仍缺决定时只问影响结果的最小问题。

## 14. 使用方式

按任务引用 PKB 的正式路径并读取相关章节，或在项目 `AGENTS.md` 中提取并写明本项目实际采用的合同；不要把 PKB 正文复制进项目形成第二份 Current。项目文档持有实际业务、入口、环境、依赖与验收；新的跨项目偏好经来源核对后只更新此处，并检查受影响的 Memory 投影。

这是一份长期协作契约，不是某个项目的一次性需求说明。
