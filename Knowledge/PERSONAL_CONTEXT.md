# 个人与工作上下文

> 用途：让新的 AI、协作者或未来的自己，在不重读历史聊天的情况下，快速理解“我是谁、我长期在做什么、我通常希望怎样工作”。
>
> 不记录：临时项目状态、版本、分支、commit、run_id、资源 ID、一次性报错或具体下一步。这些内容应留在对应项目仓库。
>
> 状态：Current
> 最后更新：2026-10-25

## 1. 我是谁

我是一个以独立站电商为核心的经营者、运营决策者和系统建设者。

我的工作不只限于营销或代码。我会同时处理商品、定价、广告、数据、网站结构、内容、联盟渠道和内部流程，并持续把零散操作沉淀为可以重复运行、验证和交接的系统。

我不是以专业软件工程师身份开展这些工作，但会深度参与业务逻辑、数据结构和自动化设计。我需要 AI 把业务语言翻译成可靠的代码和工具，同时保留我对最终逻辑、字段、流程和展示方式的控制权。

## 2. 长期业务与工作范围

## 3. 长期目标

1. 把依赖记忆和手工操作的电商工作逐步变成结构清楚、可重复运行、可校验的系统。
2. 建立统一的数据基础，让商品、销售、广告、成本、定价和经营分析能够互相连接。
3. 让系统适合当前实际操作并可以逐步扩展，而不是为了架构完整一次做得过重。
4. 降低 Colab、Google Sheets 和脚本的维护难度；出错时快速定位，不重新猜整段历史。
5. 把重要方法、决策和项目现场沉淀为知识资产，使新对话、新 AI 或新协作者可以直接接手。
6. 建立适用于多数主题的个人知识管理方式：临时思考可以自由发生，成熟内容再进入长期资料。

## 4. 思考与决策习惯

- 我通常从实际操作顺序出发，再决定系统结构。
- 我重视逻辑是否容易理解、维护和修改，不追求不必要的工程复杂度。
- 优先采用能够直接完成目标的最简单路径，验收以足以支持当前决策为目标。增加步骤前，先判断它是否会改变决策、产生必要输出或降低真实风险；如果不会，不应因为流程惯性而增加重复审计、前置检查或人工校验。已有运行证据、Current 证据或其他可靠证据覆盖主要风险，剩余事项只是用户能够直接确认的低风险身份或等价事实时，应先询问并接受用户的明确确认，不自动升级为 connector、资源级 Hash、重复发布、回读或重新执行；只有用户确认仍不能消除实际歧义，或错误确认可能造成破坏、不可逆覆盖、安全风险或业务含义变化时，才升级验收强度。
- 低风险本地迁移已有明确 Current 和可回退版本时，优先提供直接、可运行、可回退的验证步骤；只有发现实际歧义、历史取舍或破坏风险时，才升级为详细的 Git 历史与索引取证。
- Notebook 的数量和入口由业务任务及我明确的决定确定；同一任务保持清楚的职责边界和可维护性，已确认独立使用的入口保持独立。详细实现原则见 `Knowledge/Coding/CODEX_COLLABORATION_AND_LOGIC_PREFERENCES.md` §5。
- 我偏好两层信息结构，主要适用于经营报表、Dashboard、Google Sheets 和页面信息层级；不应机械套用到所有代码、技术文档或目录结构。
- 我对颜色和视觉可读性敏感。颜色应帮助区分区域、行或业务含义，不能只作装饰。
- 我会在讨论中逐步澄清真实需求。实现前应区分已确认规则、Working Assumption 和探索性想法。
- 长窗口或多轮设计进入正式编码前，应重新核对最初范围和历次确认，逐项建立 requirements-to-code 对照，不能只凭记忆实现。发现一处契约遗漏时，应同步检查配置、读取、处理、执行、结果回写、Runtime 加载和测试等相邻阶段是否仍保留旧逻辑。累计多项相互依赖的修复、版本变化或 Runtime 依赖后，应暂停继续增加补丁，先给出一次收敛视图，明确整体调用链、唯一权威 Current、模块或资产版本契约、已完成和已验证事项、当前唯一 blocker 及下一执行顺序；操作者能够理解当前系统状态后再继续实现。交付前再做遗漏审查，确认已讨论规则真实进入代码、调用顺序和贴近实际使用形态的测试，而不只确认主流程能够运行。
- 我接受 AI 做合理判断，但不希望 AI 在会改变业务含义的地方静默猜测。
- 资料不足且用户能够提供证据时，应直接列出需要的文件、命令输出、日志或截图，不要反复基于假设推进。
- 对耗时或成本较高的任务，小规模功能验收通过后可以先完成本轮收口，把全量运行留到后续；必须明确区分“小规模验证通过”与“全量完成”。
- 宣布多阶段任务完成前，必须重新对照最初范围、权威设计和后续确认，将事项区分为：已完成、已完成小规模验证、明确延期、明确取消和尚未实现。

## 5. ChatGPT、Codex 与项目收口协作

- 当前聊天拥有完整上下文时，优先由当前 ChatGPT 整理规则、Bridge Package、Source Package 或文档方案；Codex 负责本地读取、文件更新、验证和 Git 收口。
- Codex 的主要价值是维护本地项目的长期可接手性，而不只是编写或运行代码。
- 复杂项目的总体架构、职责边界、关键 Contract、主要修改点和安全恢复点已经收敛后，应主动停止无边界地继续实现；后续默认按一个 Job、一个细节或一个 bounded task 切换到独立 Chat 窗口逐项推进。换窗口前应形成正式 handoff，至少保留权威 Current 或 Git baseline、已确认 Contract、已关闭与仍开放的决定、当前 blocker 和下一安全恢复点；除非新的 Current 证据与 handoff 冲突，新窗口直接继承这些结论，不重新讨论已关闭的架构决定，也不要求用户重新解释整个项目。
- 复杂思考、代码或 Notebook 构建、项目规划和规则审查开始前，用户要求参考 PKB 时，应先根据当前任务检索相关知识，只读取命中的文件和必要章节或段落；相关内容不足时再扩大范围，不为形式完整而顺序全文读取所有核心文件。用户可以用简短的同义指令触发，不要求使用唯一固定口令。
- 使用长期知识时应区分三层来源：PKB 负责长期偏好、治理原则和 Pitfall；当前项目仓库、正式模块和用户提供的参考文件负责当前实现事实；当前聊天负责本轮目标、参数、Working Assumption 和操作授权。三层不能互相替代。
- 涉及现有项目时，已有 Current、真实调用链和已运行参考实现优先于通用经验。不得仅凭 PKB 的方向性规则自行发明 Secret 名称、认证方式、字段契约、模块路径、Runtime Adapter 或平行实现；项目证据缺失时，应明确说明缺少什么并请求资料，而不是继续补猜。
- 既有项目的迁移、handoff、Runner 对齐或代码接入中，能从 Current 可靠发现的模块路径、Job、Registry 目标、输出位置、旧名称和 helper 关系应优先 `AUTO_DISCOVER`，不要让用户先做技术考古。只有 Current 无法可靠解析时，才具体索取所缺文件、Tab、截图、日志或行，并说明用途和是否阻塞。
- 用户明确要求先检索 PKB 时，正式构建前应提供简短检索回执：实际命中的 PKB 文件或段落、实际读取的项目权威来源、准备沿用的既有契约，以及仍未取得证据的事项。
- 项目文档应让后续人员或 AI 不依赖聊天历史就能理解：项目目的、设计逻辑、当前规则、标准步骤、完成状态、唯一 Current、已废弃方向、历史 Pitfall 和唯一下一步。
- 稳定、可复用的治理规则应沉淀到 Skill；聊天窗口使用较短的 Bridge Prompt 提取当前动态事实和验收边界。阶段、数量、分支、commit、Current 代码和下一步不得永久写死在 Skill 中。
- Skill 应先形成真实任务可用的最小版本，再根据实际运行结果迭代，不必首次覆盖所有边缘情况。
- 项目收口后的 PKB 知识吸收应主动进行，但个人长期偏好不等同于本次删除、提交、发布或跨仓库操作授权；操作门禁由 PKB 的 `AGENTS.md` 管理。

## 6. 沟通与交付偏好

- 先说结论，再解释必要原因。
- 使用清楚、直接的中文；技术术语只在有帮助时出现。
- 不需要大量客套、重复总结或为了显得完整而堆砌内容。
- 生成给用户使用的 Markdown 文件时，默认采用紧凑 Markdown：减少无意义空行和连续换行，标题、字段、信息卡及关联内容尽量紧凑；确需视觉分区时才增加空行。
- 复杂需求先整理成明确规则，再动代码。
- 关键歧义应说明它会影响什么；不影响主方向的小问题可以采用合理默认值并明确说明。
- 失败、数据不完整或只完成一部分时必须直说，不能用“已完成”掩盖问题。
- 运营报告默认先给数据，再给 4–6 条面向非技术阅读者的结论。
- 需要复制到 Google Sheets 或飞书的表格，默认使用 Tab 分隔文本，不使用 Markdown 表格。
- 当一种交付方式明显更快、更容易维护时，希望 AI 主动推荐。普通数据、导入表和批量结果优先 UTF-8 CSV；确需公式、多工作表、数据验证等 Excel 功能时用 XLSX。只有展示目的、实际可读性问题或明确要求时再做相称的格式与渲染；字段、公式、编码和结构仍要按风险核对。具体文件规则见 `Knowledge/Coding/CODEX_COLLABORATION_AND_LOGIC_PREFERENCES.md` §12。
- 治理体系或 Prompt、Skill 需要整体升级且用户需要文件交付时，提供可直接执行的完整更新指令和清楚命名的完整交付件；具体交付形式由本轮要求决定，不为普通小改动默认打包。

### “本步安排”默认内容

项目或代码任务需要正式说明“本步安排”时，默认包括：

1. 当前阶段进度；
2. 设计目的；
3. 可选方案及取舍；
4. 推进价值；
5. 执行者；
6. 推荐模型；
7. 预计操作时间；
8. Token 消耗；
9. 本步不需要做的事项。

不适用项应标记为不适用，不为凑齐格式增加无价值步骤。

## 7. 代码与 Notebook 协作

- Notebook 打开后先用简短中文说明运营人员如何准备、设置参数、运行、看结果及处理失败；内容以代码真实行为为准。详细边界见 `Knowledge/Coding/CODEX_COLLABORATION_AND_LOGIC_PREFERENCES.md` §5.4。
- 同一本 Notebook 需要按任务要求支持 Google Colab 与本机 VS Code/Jupyter 等已有环境，保持单一业务逻辑；具体依赖、路径、Secret 与运行验收以项目 Current 为准。日常认证优先沿用已有配置并非交互运行，先查现有说明和代码，缺口具体指出，不把 OAuth 点击当成我的默认偏好。
- 同类表格公式优先设置首个适用单元格，再用填充或扩展覆盖目标范围；Notebook 不逐行写同类公式。
- 长任务要有适度进度，失败与部分完成要说清楚；复杂交付需要完整可用文件，不能让我自行拼接补丁。
- 代码、Notebook、认证、公式、写入、运行摘要与验收的详细原则统一见 `Knowledge/Coding/CODEX_COLLABORATION_AND_LOGIC_PREFERENCES.md` §4–§12；故障条件和验证见相应 Pitfall。这里的支持目标不代表任何现有项目已完成双环境验收。

## 8. 文件与版本管理偏好

- 正式 Current 使用稳定身份并原位更新，普通历史由 Git 保留；备份和 Archive 按风险及独立追溯价值决定。外部交付文件名要能与旧附件区分，但不能改变仓库中的正式路径或模块身份。
- 文件、Runtime 副本、环境、Secret、旧资产处理及交付边界详见 `Knowledge/Coding/CODEX_COLLABORATION_AND_LOGIC_PREFERENCES.md` §5、§10、§12 和 P022、P054、P060。

## 9. 数据与输出原则

- 业务口径先于图表和代码；同名指标说明时间范围、粒度和计算方式。输出应让经营者能读懂、追溯来源与运行配置，不因技术便利改变已确认的业务定义。
- 日常 Operator 型工具，在项目 Current 没有相反契约时，我默认更偏好 Google Sheets 作为主要操作界面；本地文件是正式来源还是缓存、快照或备份，必须由项目合同决定。长任务是否以本地文件为 Source of Truth 同样按实际工作流决定，不能从“需要断点恢复”自动推断。
- 普通数据交付优先 CSV；必要功能再用 XLSX，确有展示或可读性需要才格式化与渲染。详细数据口径、同步边界、视觉规则和校验见 `Knowledge/Coding/CODEX_COLLABORATION_AND_LOGIC_PREFERENCES.md` §4、§6–§9、§12。

## 11. 更新规则

- 只有长期稳定、会影响未来判断的信息才进入本文。
- 新信息与旧信息冲突时，以用户最近一次明确表述为准，并原位更新旧条目。
- 相同偏好只保留一个主条目；需要关联 Pitfall 时使用简短引用，不复制完整事故说明。
- 每次重大更新修改“最后更新”日期；历史由 Git 保存，不在正文堆叠流水账。
- 已经明确沉淀的长期协作偏好应在后续任务中默认执行，不要求用户反复重新说明。
- 本文不构成破坏性操作或 Git 写入授权；仓库操作边界以 `AGENTS.md` 为准。
