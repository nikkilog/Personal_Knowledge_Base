# AGENTS.md

本文件定义当前项目及其子目录的长期通用工作规范。除非更深层目录存在自己的 `AGENTS.md`，否则所有代码、Notebook、数据处理和文档任务均遵守本文件。

## 1. 工作原则

1. 先理解业务目标、输入、输出、粒度、唯一键和验收条件，再实现。
2. 优先选择简单、可读、可维护的方案；不要为了抽象而抽象。
3. 不改变未被要求改变的业务逻辑、文件、Sheet、字段或格式。
4. 发现关键歧义时明确指出；不会改变主方向的小缺口可采用保守默认值，并在结果中说明。
5. 任何失败、不完整、降级或未经验证的结果都必须明确报告。

## 2. 语言与注释

- 面向用户的说明、代码注释、配置说明、日志解释和异常消息默认使用中文。
- API 字段、代码标识符、库名、协议名、产品名和既有 Sheet 名保留英文原文。
- 注释重点解释“为什么这样做”和业务口径，不逐行复述代码。
- 复杂函数必须有简短 docstring，说明用途、关键参数、返回值及可能抛出的异常。
- 禁止保留误导性注释、与代码不一致的示例或大段已失效的注释代码。

## 3. 命名规范

### Python

- 变量、函数、模块：`snake_case`。
- 常量和人工配置项：`UPPER_SNAKE_CASE`。
- 类名：`PascalCase`。
- 布尔值使用可直接判断真假的前缀，如 `is_`、`has_`、`should_`、`enable_`、`allow_`。
- 函数名优先使用“动词 + 对象”，如 `load_campaign_daily()`、`validate_required_columns()`、`write_overview_sheet()`。
- DataFrame 名称体现内容与粒度，如 `campaign_daily_df`，避免 `df1`、`temp2`、`final_final`。
- 日期变量明确边界，如 `date_from`、`date_to`；金额、比例和时区不得只靠猜测变量名理解。

### 文件与 Notebook

- Notebook 使用能说明阶段和动作的名称，优先采用 `Create_`、`Build_`、`Run_` 前缀。
- 正式主文件保持稳定名称；重大变更备份使用可排序时间版本：`name__vYYYY.MM.DD.NN.ext`。
- 禁止使用 `final_final`、`new2`、`最新版` 等模糊版本名。
- 方法论文档和项目现场文档分开；同一主题只保留一个明确的 `CURRENT` 入口。

### Sheets 与数据集

- 沿用既有 Sheet 名和字段名，除非用户明确批准重命名。
- 新名称应短、稳定、含义明确，并体现时间范围或粒度（如适用）。
- 唯一键必须在代码或文档中明确，不使用显示名称替代稳定 ID，除非业务规则就是如此。

## 4. 代码结构

- 配置、常量、字段映射和阈值集中管理，不散落在多个函数或 Cell。
- I/O、业务转换、校验、写入尽量分层，避免一个函数包办整个流程。
- 公共逻辑提取为小而清楚的函数；只有一次使用且非常简单的逻辑不必过度封装。
- 避免隐藏的全局状态。函数应尽量显式接收输入并返回结果。
- 不使用裸 `except:`；捕获具体异常，并保留原始异常上下文。
- 不静默跳过坏数据。若允许跳过，必须计数、记录原因，并反映在运行摘要中。
- 不硬编码 Secret、令牌或密码。只引用 Secret 名称或环境变量名。

## 5. Colab 规范
- Cell 1 必须是统一 Controller，集中放人工配置：项目、日期范围、运行开关、阈值、输入输出位置等。
- 必须授权时，授权 Cell 紧接 Cell 1；不得运行到流程中段才弹窗。
- 主流程应支持自上而下顺序运行，不要求用户中途修改隐藏变量。
- 顶部维护版本号、变更记录和运行说明。
- 默认不随意创建新 Sheet Tab；按已确认规则对同名目标执行清空并全量写入或覆盖。
- DRY RUN 与正式写入必须清楚区分；DRY RUN 不得产生外部写入。
- 结束时输出运行摘要；适用时包括：`run_id`、读取行数、待处理行数、计划写入行数、实际写入行数、警告数、错误数、输出视图和耗时。

## 6. 数据处理规范

- 在处理前验证：输入存在、数据非空、必需字段齐全、字段类型和日期范围合理。
- 明确记录：数据源、时间范围、时区、粒度、唯一键、去重规则、空值规则和汇总口径。
- 金额、百分比、ROI/ROAS、CPA 等指标应在代码中明确单位和公式。
- 合并前检查键的唯一性及预期关系（1:1、1:N、N:1）；发现意外行数膨胀时立即失败。
- 写入前验证行列规模，防止超过 Sheet 网格范围。
- 关键写入后进行与风险相称的校验，例如回读、行数、字段、主键唯一性、汇总值或写入范围核对。
- 不用空 DataFrame、全零结果或旧缓存冒充成功运行。
- 近期会重新归因的数据可输出 WARNING；是否允许容差必须由明确配置控制，不能在代码中偷偷放宽。

## 7. 输出与展示

- 先给结论，再给必要证据和细节。
- 面向非技术阅读者的报告：先数据表，再给 4–6 条可行动结论。
- 需要复制到 Google Sheets 或飞书的表格默认输出 Tab 分隔文本，不使用 Markdown 表格。
- 代码或数据文件交付时，说明文件用途、运行入口、关键配置和验证结果。
- 可视化必须帮助区分业务块、行或指标；不要为了装饰增加层级、颜色或图表。
- Sheet 默认遵循两层表头习惯；数据区可用分块色和斑马线帮助防止看错行，字段列避免无意义着色。
### 文档结构规范
-   工具、脚本、组件类说明优先使用信息卡结构，不使用长 Markdown 表格。
-   Markdown 表格只用于字段少、长度短、需要横向比较的信息。
-   长字段、参数列表、工具说明、资产索引优先使用固定标题结构。

推荐格式：
``` md
## 文件名

**用途**

一句话说明。

**输入**：xxx  
**输出**：xxx

**什么时候用**

- xxx
- xxx

**Size**：Configurable

```text
参数名
```

**主要修改参数**

``` text
参数列表
```

-   文件名负责快速识别能力。
-   正文负责说明用途、默认配置、适用范围和限制。
-   不应把默认参数值误认为工具能力。
-   同类工具文档应保持统一结构，便于 AI、新协作者和未来自己快速接手。


## 8. 优先库与工具

在满足现有项目依赖的前提下，按以下偏好选择：

- 路径与文件：优先 `pathlib`，不要到处拼接字符串路径。
- 表格与数据转换：优先 `pandas`。
- Parquet：优先 `pyarrow` 引擎。
- XLSX：优先 `openpyxl`；需要保留复杂既有格式时先确认兼容性。
- Google Sheets 简单读写：优先 `gspread`；批量格式、网格调整或复杂请求使用官方 Google API client。
- Google Drive 与其他 Google API：优先官方 `google-api-python-client` 和官方认证库。
- HTTP 同步请求：优先 `requests`；只有确有并发或异步需求时引入 `httpx`/`aiohttp`。
- 数据校验：简单规则优先显式 Python 校验函数，避免仅为少量规则增加重型依赖。
- 命令行搜索文件与文本：优先 `rg` / `rg --files`。
- 修改现有文件时，优先最小差异修改；不得覆盖用户无关改动。

引入新依赖前应确认：现有环境是否已安装、是否真正降低复杂度、Colab 是否容易复现。能用标准库清楚完成的简单任务，不额外增加依赖。

## 9. 错误与日志

- 关键失败必须抛出异常或以非零状态结束，不得只打印一行后继续假装成功。
- 异常消息至少说明：哪个阶段失败、失败对象、预期值、实际值；适用时给出修复方向。
- 日志使用稳定阶段标签，例如 `[START]`、`[OK]`、`[WARN]`、`[FAIL]`、`[SUMMARY]`。
- 长任务提供心跳信息，但避免逐行刷屏；心跳应包含耗时和可理解的进度指标。
- WARNING 必须可汇总、可追踪；不得用 WARNING 掩盖本应终止的错误。
- API 错误保留状态码、错误类型和必要上下文，但不得输出 Secret 或完整敏感响应。

## 10. 测试与验收

- 修改后至少执行与风险相称的验证：语法检查、单元测试、小样本运行、DRY RUN 或目标环境回读。
- 修复 Bug 时尽可能增加能复现该问题的测试或断言。
- 验收不只看“代码运行完”，还要核对业务结果、行数、关键汇总和输出位置。
- 无法执行某项验证时，在交付中明确列出“未验证项”和原因。
- 不把 WARNING、跳过或部分成功描述为全部通过。

## 11. 安全与变更边界

- 不记录或输出 Secret 值、访问令牌、密码、私钥和完整认证文件内容。
- 不执行破坏性操作，不删除或覆盖用户资料，除非用户明确要求且目标范围已确认。
- 不擅自创建额外 Sheet、Drive 文件、远程分支、提交或发布内容。
- 修改现有项目时先检查工作区状态，保留与当前任务无关的用户改动。
- 对外部系统的正式写入必须受明确开关控制，并优先提供 DRY RUN。

## 12. 文档与交接

- 方法论/白皮书记录跨项目原则、架构选择、判断标准、常见问题和解决方案。
- 项目交接文档记录真实现场：目标、范围、正式文件、版本关系、输入输出、配置、资源位置、Secret 名称、完成项、验证结果、限制、故障修复、运行方法、验收标准和下一步。
- 不把临时 ID、当天进度或一次性报错塞进通用规范。
- 文档必须让新对话或新协作者无需重新猜历史即可继续工作。

## 13. 完成定义

任务只有在以下条件满足后才能声明完成：

1. 请求范围内的产物已经创建或修改。
2. 已执行适当验证，且结果明确。
3. 没有把失败、部分写入或未验证内容伪装为成功。
4. 交付说明包含产物位置、主要变化、验证结果和仍存在的限制。
5. 未泄露 Secret，未破坏无关内容，未超出用户授权范围。
